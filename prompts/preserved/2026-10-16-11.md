**What an actual records system would do, in plain terms:**
- **Look up anything by ID** with everything linked to it: what it continues, what corrected or replaced it, what closed it. You'd get the current answer and its history together.
- **Answer "what's the current ruling on X?"** across the record, the audit index, the dispatches and forager-forecast's decision log in one search, with replaced rulings marked.
- **List open work:** intents with no closing entry, and decisions marked "not authorised" or held.
- **Hand out the next free ID safely,** so two planners can't take the same one.
- **Cite its answer:** every result comes with file, line and commit. That makes "check from source" one command and gives you something citable.

**Three ways to build it**, from smallest to largest:

| Option | What it is | Main tradeoff |
|---|---|---|
| A. A lookup tool over the existing files | One small tool that reads the records as they are. The markdown stays the source of truth, append-only and in git. | Cheapest, and works on Forager's 1,279 entries today. The single file is still a merge-conflict point. |
| B. One file per entry, plus the tool | Each entry becomes its own file in a records folder. | Ends the merge conflicts and the giant file. Needs a format change, and a cutoff or migration for history. |
| C. A database service | Records live in a hosted database behind an API. | Best querying. But the source leaves git, so it needs its own history, backups and append-only guarantees, and it's outward-facing. |

I'd start with A. It serves the rule immediately without touching how anything is written, and B can come later if the merge conflicts keep costing time. Either way it's a build, so the first step would be a short spec for you to approve, not code.
